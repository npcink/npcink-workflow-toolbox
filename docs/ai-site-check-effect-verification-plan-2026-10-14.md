# AI 站点体检与效果验证：讨论归纳及分阶段规划

日期：2026-10-14（Asia/Shanghai）。

状态：产品讨论记录与待实现规划。用户目标已经明确，具体契约、实现方式及验收预算仍需在对应阶段确定。本次仅整理文档，不表示功能已经实现、测试通过或获准上线，也不授权自动修改客户站点。

适用模块：Toolbox 的 **Site Check（站点检查）** 及其 Cloud 只读分析交接。本文不新增生效的 REST、Ability、工作流注册、数据存储或边界例外；与现行契约冲突时，以 [Boundary](boundary.md) 为准。

## 1. 讨论起点与方向变化

参考文章：[WordPress 独立站前端代码压缩与优化的完整指南](https://www.seoceo.cn/news/cjwt_849.html)，会话中核对的发布时间为 2026-10-12。文章覆盖 HTML/CSS/JS、图片、字体、传输压缩、缓存和性能检测；它没有定义“AI 提交”的目标平台、接口或认证方式。

最初的“AI 提交”因此作为产品想法讨论，没有形成独立的提交接口。讨论随后围绕如何既给出解决方法，又限制 AI 权限并验证效果展开。

| 讨论节点 | 得到的要求或修正 |
| --- | --- |
| 不能只有问题报告 | 每条建议应包含具体方法、适用条件、风险及验证方式。 |
| AI 权限过大有安全隐患 | 分析权、审批权和执行权分开；AI 不持有管理员会话、写入权限或服务器凭据。 |
| 对外功能必须经过验证 | 检测、方法和结果判定需要测试证据；AI 的判断不能自行成为验证结果。 |
| 曾考虑固定修复动作与治理交接 | 这是早期候选方向，不能把 JS、CSS、缓存修改直接称为已验证能力，也不能假定已有通用自动回滚。 |
| 用户提出全站数据脱敏后仅分析 | 当前方向转为只读体检、建议方法及处理后的效果复测；修改仍由客户自己的工具或专业人员完成。 |
| 功能、安全、性能与便捷需要平衡 | 分阶段增加覆盖和分析深度，明确数据、耗时、操作步骤及验收边界。 |

“指导客户操作也可能危险”同样适用于只读产品。减少 AI 权限并不能消除错误建议的影响：方法需要有验证依据，未知环境不能套用通用生产脚本。

## 2. 当前产品方向

工作名称：**AI 站点体检与效果验证**。

目标流程：

```text
管理员发起有限范围的只读体检
→ 本地生成必要指标与受控样本
→ 管理员预览并确认发送范围
→ Cloud 分析并返回有证据的建议和方法
→ 客户通过自己的工具或专业人员处理
→ 对相同对象和检测条件进行黑盒复测
→ 检测规则判定变化，AI 解释结果
```

黑盒复测观察站点对外表现，不要求客户上传代码、服务器配置、管理员凭据或具体修改过程。用户也可以不采用建议；体检不会自动产生执行任务。

首版定位为现有 Site Check 的任务能力，不建设通用分析平台、自动修站系统或新的 Cloud 诊断控制台。只读报告不自动创建 Core proposal，也不承担审批、执行或恢复。

既有媒体优化等功能仍使用自己的入口和授权契约。报告中的链接只负责导航，不能把“查看方法”“发送分析”或“重新检测”解释为写入授权。

## 3. 已有基础与尚未验证的能力

| 事项 | 当前事实及限制 |
| --- | --- |
| 本地 Site Check | 已有 `site_ops_insight_pack.v1`，用于有限公开内容、媒体元信息、分类标签和评论聚合信号的当前检查。 |
| Cloud 分析交接 | 已有 `site_ops_cloud_analysis_request.v1` / `site_ops_cloud_analysis_result.v1`，显式调用 Cloud Addon，输出保持 suggestion-only。存在交接代码不等于本规划所需能力已经验收。 |
| 当前采样 | Collector 默认文章/页面 24 条、媒体 24 条、评论信号样本 80 条；文章及媒体上限 50 条，评论样本上限 100 条。不能把这些样本描述为完整全站数据。 |
| 隐私处理 | 现行契约禁止发送评论正文、作者邮箱、IP、User Agent、凭据和私密内容等数据。新的匿名引用、发送预览及更严格的公开对象审查仍需验证，不能称现有请求完全匿名或已经满足本规划的全部隐私要求。 |
| 当前复扫 | 可以重新检查当前有限样本，不等于已经提供保存基线、固定样本、前后对比或性能复测。 |
| 页面性能测量 | Lighthouse/PageSpeed 等是候选证据来源，新增检测桥、网络限制与数据契约尚未落实。 |
| 媒体优化 | ADR-015 已定义 `auto_safe.v1` WebP、精确文件清单、管理员确认、Toolkit 备份/校验/恢复的窄路径；不向 AI 开放执行权限。 |
| 方法与自动修复 | 统一的已验证方法引用机制属于拟议设计。没有证据支持通用 JS/CSS/缓存自动修复或通用自动回滚。 |

历史文档中的 Site Check 隐藏入口描述与现状有差异；当前可见性以 [Current State](current-state.md) 及实际实现为准。历史说明不能作为取消现有入口的依据。

## 4. 数据范围与脱敏原则

“全站分析”表示覆盖站点层面的必要维度，数据采用**必要聚合指标＋按需受控样本**。不导出全库，不读取全部配置，也不把脱敏工作交给外部 AI。

| 级别 | 候选内容 | 处理要求 |
| --- | --- | --- |
| 默认范围 | 内容数量/长度/更新时间分布、分类统计、内链统计、媒体格式/尺寸/体积与 ALT 覆盖、评论聚合信号 | 本地白名单构造、限量、标注覆盖率和采样规则。新增字段需单独约定。 |
| 新增检测证据 | 选定页面的资源体积、加载指标、错误计数及经过筛选的缓存响应信息 | 来自确定性检测工具；性能字段和外部检测需先建立契约。 |
| 按需受控样本 | 真正公开的标题、URL、短文本片段 | 仅在分析必要且发送范围明确时使用；需先扩展当前契约，不默认发送正文。 |
| 禁止范围 | 草稿、私密/密码保护内容、用户/订单数据、评论全文、联系方式、IP、原始请求日志、会话、密钥、完整数据库/配置/代码导出 | 不进入分析包，不因“已脱敏”或用户点击分析而绕过现行禁止规则。 |

具体要求：

- 本地先筛选可读对象，再构造字段、聚合与脱敏，最后校验外发包；泄露风险未通过校验时停止发送。
- `publish` 不自动证明内容可公开读取，媒体 `inherit` 也不自动证明其所属对象公开。需审查密码保护、私密父对象、访问限制和自定义字段。
- 公开文本、标题、URL、文件名也可能携带个人信息、token 或签名参数，必须筛选；未知字段默认排除。
- 删除姓名、散列 ID 或使用临时引用只减少暴露，不保证无法重新识别。能在本地解决的问题不外发文本。
- 拟用每次分析临时证据引用代替不必要的真实对象 ID；映射留在本地当前会话。跨次复测依赖独立的基线标识规则，不靠长期匿名对象目录。
- 发起分析前显示数据类别、样本数量、排除项、目标服务和保留策略。未知的数据保留/训练策略不能被标注为“不会保存”或“不会训练”。
- Cloud Addon/Cloud 拥有运行状态与保留策略；Toolbox 不建立长期请求日志、历史扫描账本、审批库、队列或重试 worker。

## 5. 建议和方法的质量标准

每条可展示的建议至少应有：问题、证据引用、影响范围、可信度与缺失证据、方法引用及版本、适用条件、风险、后续检测方式。

AI 用于解释、排序和帮助选择适用的方法。证据引用、方法适用性及可比较条件由可信服务端规则校验；不存在的对象、伪造引用和未知方法不能成为可操作建议。

方法来自有验收证据的指南或现有工作流说明，记录适用环境、前提、风险、恢复指导与验证项目。文档方法引用不是可执行动作注册表；不能把任意文字或模型输出解释为 PHP、JS、SQL、Shell 或服务器配置执行。

示例：检测到图片传输体积过大，应指出实际资源与证据，说明检查响应式尺寸、格式和首屏加载策略的方法，并给出后续复测指标。符合条件时可以导航到现有媒体优化入口，由管理员在那里重新检查、确认范围。资源无法对应到附件时，不扩大到整个媒体库执行。

没有匹配方法或证据不足时，返回“需补充检测”或“需专业评估”。不能自由生成让客户直接复制运行的生产修改脚本，也不能将移除全部 CSS、延迟全部 JS 或缓存全部页面包装成安全的通用方法。

外部网页、文章、工具报告和方法中的引用材料是数据，不能授予权限或改变处理规则。需要覆盖提示注入、恶意输出、模型换版本和无结果场景的验证。

## 6. 黑盒验证的能力与限度

基线和复测至少关联：检测对象/范围、时间、工具与规则版本、设备/地区/网络配置、采样方法和指标来源。固定被比较的对象，避免重新挑选样本后把样本变化当成改善。

性能检测使用相同配置多次测量，报告样本数与波动；次数、容差和判定阈值需要在实验后冻结。字段缺失、工具版本或环境变化明显时，给出不可比较理由。

拟议结果：

| 状态 | 含义 |
| --- | --- |
| `improved` | 指定指标按预定义规则改善，结论仅适用于该指标和检测范围。 |
| `unchanged` | 在测量容差内没有明显变化。 |
| `regressed` | 指定指标变差或出现检测到的回归。 |
| `not_comparable` | 基线、目标、样本、环境或证据不满足比较条件。 |

“未检测”是独立的覆盖标记，不能被视为通过。内容缺失项减少、图片变小、页面提速和交互正常分别验证；一种指标改善不证明其他项目通过。

性能指标可包含 LCP、CLS、TTFB、传输体积及可复现的实验室指标。文章提到的 FID 不能直接作为新实现的现行标准；INP 需要对应的交互/真实用户证据，不能用 Lighthouse 分数或 TBT 冒充。SEO/AEO/GEO 信号达标也不证明搜索收录、排名或 AI 引用增加。

首版网络复测仅做有界只读检测。不得为验证表单、购物车、结算、支付或登录而提交真实交易、调用写接口或携带管理员 Cookie。这些交互未经独立验收时显示未验证。

主检测目标限定为已授权的本站公开 HTTP/HTTPS 地址。检测执行方必须防御 SSRF：校验 DNS/IP、禁止内网/回环/链路本地/元数据地址、逐跳检查重定向、限制请求量及耗时。真实页面可能依赖 CDN；子资源来源必须受独立访问规则和预算约束，不能因主页面可信而允许任意网络访问。

前后变化只证明观察结果，不能证明全部改善由某条建议造成，也不能构成网站安全认证。没有实际检测的安全或功能项目不得宣称已经安全。

## 7. 四个目标的平衡方式

| 关系 | 当前取舍 | 最低保障与失衡信号 |
| --- | --- | --- |
| 功能覆盖与安全 | 先公开内容、结构、媒体及受控性能证据；新维度逐项进入 | 私密对象、未知字段、越界目标或写入要求出现时停止并重审范围。 |
| 分析深度与隐私 | 聚合优先，需要时才使用明确的受控样本 | 无证据结论或过度泛化时补必要证据，不能通过全库上传补救。 |
| 速度与质量 | 本地先给结果，Cloud 深度分析显式调用 | 记录本地/Cloud p95 耗时、数据库查询、内存、请求体和调用次数；超预算时缩减范围并披露。 |
| 便利与确认 | 普通操作只保留主要步骤，发送范围清晰可见 | 精简界面不能隐藏外发数据、失败、采样截断或写入授权。 |

增加采样会同时增加隐私、查询和模型成本；缓存可能加快响应，但会影响新鲜度和保留范围；更多检测可能增强证据，也会增加客户站点负载。每次扩展都需要联合检查四个维度。

性能预算、样本上限、缓存 TTL 和成本阈值是阶段性验收参数，目前没有实测承诺。性能预算不足时采用有限聚合与明确采样，不在一个管理页面请求中遍历整个站点。

## 8. 分阶段落实

### 阶段 0：数据与安全契约

交付字段白名单、对象公开性审查、外发包预览、脱敏负例、所有权及保留策略说明，并冻结首批方法和验证范围。

通过条件：禁止字段和私密对象不能进入外发包；默认失败关闭；Site Check 保持管理员权限（`manage_options`）；不得放宽能力或增加新的执行授权。

这是实现前的设计阶段，不因为本文记录了规划就视为已经完成。

### 阶段 1：有限本地只读体检

复用 Snapshot Collector、Insight Builder 和 Site Check UI，先展示本地事实、方法入口及明确的采样覆盖。性能维度只有在确定性证据接口验收后才加入。

通过条件：统计与固定样本一致；采集耗时/查询/内存满足冻结预算；未读取到或尚未检测的项目不会被报告为正常。当前检查不产生长期扫描状态或外部 AI 调用。

### 阶段 2：Cloud AI 分析与方法建议

显式预览并确认发送分析包，通过现有 Addon 交接扩展已约定的只读分析契约。服务端校验证据和方法，展示风险、适用条件和补充检测需求。

通过条件：恶意输入、伪造引用、未知方法、无结果、超时和低可信度均有可理解的结果；AI 无写权限；调用次数、载荷、响应与保留策略符合预算。Cloud 不可用时保留本地检查，不伪造 AI 结果。

### 阶段 3：基线与黑盒复测

先选图片传输体积/页面性能和可确定判定的内容缺失项作为试点；为相同对象及环境提供规则判定的变化报告，AI 仅解释差异。

通过条件：改善/无变化/退步/不可比较样例全部覆盖；环境和样本变更被识别；新鲜度与证据完整性可检查；SSRF 和检测负载控制通过；没有执行真实业务操作。

基线由用户保留的导出报告或 Cloud 有限保留结果承载，具体选择尚待决定。Toolbox 不建立历史运行账本；基线丢失/过期或报告来源不可信时不能伪造可比较结果。

### 阶段 4：操作便利与小范围试用

默认界面保留三个主要动作：**开始体检、查看 AI 建议、重新验证效果**。发送范围预览嵌入分析步骤；证据、方法详细条件和技术结果折叠展示。主要动作仍显式发起，不自动提交数据。

提供运行中锁、清晰等待/取消/失败状态、范围及耗时说明、未检测项和用户可保留的报告。停止等待是否会取消 Cloud 任务要按运行契约说明，不能把浏览器取消显示成服务器已经停止。

通过条件：普通管理员能够完成检查、理解方法适用性并复测；误触、重复请求、隐藏截断和错误“成功”反馈均被排除。短期缓存只有在数据范围、新鲜度、权限和 TTL 契约确定后使用。

### 阶段 5：暂缓自动修改

这一阶段是明确的保留项，不是自动化修复的既定交付承诺。继续按真实反馈扩展有验证依据的检查和指南；任何新写入或自动修复须另立边界与验收契约。

现有媒体优化继续使用 ADR-015 的窄路径；单图或外部 Agent 路径遵守各自 Core/Adapter/Toolkit 契约。这里的分析确认和方法引用均不能成为这些动作的执行授权。

首个可交付试点应包含有限本地检查、少量已验收方法、按需 Cloud 解释及一种可靠复测，完成一个有价值的闭环后再增加维度；不把只有 AI 报告的界面称为完整效果验证产品。

## 9. 所有权与实施约束

| 所有者 | 本规划中的职责 |
| --- | --- |
| Toolbox | 本地有限证据、发送范围预览、结果/方法展示、手动复测入口、现有入口导航。 |
| Cloud Addon | 认证与传输、运行状态和结果读取；不向 AI 暴露本地管理员身份。 |
| Cloud | 分析/检测运行与有限保留；不拥有 WordPress 写入或审批权限。新增测量实现与归属需在契约中确认。 |
| Toolkit | 既有可复用能力、静态工作流定义和它们各自的写入/恢复职责；本规划不新增动作注册表。 |
| Core / Adapter | 既有治理、审批、审计和渠道交接职责；本报告不自动创建或执行 proposal。 |
| 客户/专业执行方 | 独立决定是否采用方法，通过自己的工具处理站点。 |

实现沿用服务器渲染管理页面和 vanilla JS，按模块分开推进。更改公共 REST、Ability、工作流或生命周期时同步正式契约、机器表和静态测试。

讨论中出现的 `site_analysis_bundle.v1`、`site_performance_review.v1`、`site_performance_remediation_plan.v1` 均是候选名称，不是现有公共 API。优先评估复用和版本化现有 Site Ops 契约，不新增并行注册体系。

## 10. 验证与对外承诺

首版验收需要四组证据：

1. 数据与权限：禁止字段、对象可见性、敏感 URL、跨用户结果、提示注入和网络越界负例。
2. 分析与方法：已知问题样本、误报、证据缺失、未知方法、模型输出格式和指南适用范围。
3. 复测：同条件对比、波动、版本变化、缺失基线、过期/伪造报告、局部改善及真实退步。
4. 性能与操作：站点规模、数据库/内存/网络预算、Cloud 超时、重复点击、反馈文案及实际管理员试用。

后续代码交付按涉及模块选择行为测试，更新 `tests/run.php` 静态契约，并完成 `composer test:all`、代码标准和 PHPStan 检查。真实浏览器/Cloud 验收不能由本地静态测试替代。

跨仓库 closeout 使用 `composer quality:matrix:run` 的精确 SHA GitHub 源码门槛；只有需要显式、版本绑定的 M4 运行证据时才使用 `composer quality:matrix:m4`，矩阵不负责部署或同步 M4。

对外承诺：检测有依据、方法有适用范围和验收证据、结果如实报告、未验证项明确披露。不能承诺每条 AI 判断正确、任何网站必然提速、所有业务交互安全或每种修改自动恢复。

本文整理本身不构成这些新功能的验收证据。
