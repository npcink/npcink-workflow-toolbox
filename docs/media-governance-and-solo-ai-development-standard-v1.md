# 媒体治理与单人 AI 开发规范 v1

状态：当前开发与灰度执行规范。

## 1. 目的

本规范把媒体优化和单人使用 AI 开发时反复出现的经验，整理成一条可验证、可恢复、可暂停的工作方法。目标不是一次性把所有图片处理完，而是让每一次改变都能回答：改了什么、证据是什么、出了问题如何停下和恢复。

## 2. 产品目标与边界

媒体优化的用户流程固定为：

```text
选择范围 -> 检查效果 -> 一次确认并运行 -> 历史与恢复
```

WordPress 负责媒体清单、权限、确认、文件替换、备份、引用和恢复；Toolkit 负责本地写入；Addon 负责传输和 Cloud 调用；Cloud 负责转换事实、编码和质量判定。Cloud 不成为 WordPress 控制面，也不保存长期媒体文件。

本功能只处理静态 JPEG、PNG、WebP。默认输出 WebP，保留 15% 最低节省门槛和 25% 轻微缩放上限；不处理 GIF、动画 WebP、视频、孤儿文件或 CDN 重写。

当前附件文件永远不是自动清理目标。所谓“删除原图”，仅指删除替换前保存的专用备份副本，且必须满足下文的 30 天和确认规则。

## 3. 文件版本与视觉证据

`media_fingerprint` 只能是当前附件主文件真实字节的 SHA-256，格式为 `sha256:<64 位小写十六进制>`。附件 ID、URL、文件名和修改时间都不能证明文件内容没有变化；媒体元数据摘要另存为 `metadata_fingerprint`。

预览只产生短期结果，不写入当前指纹、视觉证据或替换历史。应用替换前和真正切换文件前各校验一次源指纹，替换成功后计算新指纹，并记录：

- `new_media_fingerprint`；
- `derived_from_media_fingerprint`；
- `transform_type`；
- `visual_reuse_policy`；
- `transform_facts`。

视觉证据只有在当前文件指纹匹配时才能直接复用。替换后的文件还必须有可信 lineage、完整转换事实且策略允许复用。无损编码或仅元数据变化可以直接复用；普通有损压缩或不超过 25% 的缩放只能作为“待人工确认候选”；裁剪、水印、去背景、透明通道丢失、超过 25% 缩放、未知变换和第三方直接覆盖必须重新识别。指纹失配时，ALT 回退文章上下文，媒体推荐拒绝旧描述，并进入既有识别计划。

事件只负责快速标记，不能代替完整扫描。Addon 保留 WordPress Hook、Toolkit 版本变化事件、完整媒体扫描和使用前指纹校验四层兜底；重复事件、扫描和网络重试必须幂等。

## 4. 默认优化与备份清理

默认优化使用 Cloud 的 `auto_safe` 策略：普通用户不接触质量、编码器、Artifact、Provider、模型或 embedding 参数。一次运行最多冻结 1000 张清单，前台每 10 张为一个处理块；每项独立失败，不影响其他项。

每次成功替换都保留专用备份，并在历史中保存批次、源指纹、新指纹和恢复状态。默认恢复期为 30 天：

1. 30 天内可恢复指定图片或整个批次；
2. 只有专用备份目录中的备份才可能清理；
3. 过期后先生成只读预览，再由管理员明确确认；
4. 可选的自动清理必须是管理员显式打开的设置，不能由普通用户流程默认开启；
5. 清理只删除过期备份并保留 `backup_expired` 历史，不删除当前附件。

没有过期目标时，确认调用应保持无删除结果；路径不在专用目录、历史不完整或文件状态不确定时跳过并报告。

## 5. 灰度与停止线

生产媒体库不采用一次性全库验证。执行顺序为 10 张以内低风险样本、50 张小批、再按证据逐步扩大。每批开始前记录附件 ID、源 SHA-256、MIME、尺寸、引用位置和预计收益。

每项替换后检查：新文件可解码、MIME 和尺寸、WordPress metadata、文章和页面引用、缩略图、REST 信息、replacement history、备份和新指纹。至少恢复一项，再做整批恢复；失败项必须隔离，不得无差别回滚成功项。

出现 5xx、引用错误、指纹不一致、备份缺失、重复执行、锁冲突、输出变大或收益不足时，立即停止下一批并保留现场。502 只按阶段定位：先看请求是否到达、Cloud/Addon 超时、下载校验、WordPress 写入和代理日志；在同一传输签名连续失败两次后停止盲目重试，改走已记录的恢复路径。

## 6. 单人 AI 开发工作法

一个人开发时，把 AI 当作并行的调查和验证助手，把 Git、共享运行时和发布保持串行：

1. 每个任务先写变更包：模块、目标、非目标、合同、文件、验证、回滚；
2. 主工作树脏时，从最新基线建立干净 `codex/*` worktree，立即加锁；
3. 只提交当前任务文件，绝不在混合工作树使用 `git add -A`；
4. 先跑最窄测试，再跑跨仓矩阵；不要用重复全量测试制造安全感；
5. 把 `local verified`、`candidate validated on M4`、`PR verified`、`merged into master`、`accepted on M4` 和 `production validated` 分开记录；
6. M4 是运行时证据，不是源码真相；Cloud 主树脏时用隔离 worktree，不能声称 clean exact-SHA；
7. 定时任务只做只读审计、状态汇总和下一步提醒。涉及 WordPress 写入、备份删除、M4 操作、push、PR、合并或部署，必须在当前任务中重新获得明确授权。

## 7. 自动化任务设计

推荐保留一个每周阶段提醒，按“旧任务恢复 -> 备份清理 -> 小批灰度”顺序检查，状态无变化时保持安静。自动提醒必须输出证据和阻塞原因，不替用户做破坏性决定。

不建议默认启用自动 checkpoint、自动 push 或自动合并。若以后启用，必须限制到干净、非默认、非受保护分支，保护活跃会话和锁定 worktree，并在 push 前运行 secret scan 和窄门检查。

## 8. 收口模板

每次阶段结束至少记录：

```text
目标与范围：
实际变更：
通过的测试与运行证据：
跳过或失败的检查及原因：
最高证据状态：
回滚方式：
下一步及所需授权：
```

一句话原则：先证明文件是什么，再证明谁在使用；证明转换有效后才切换，观察稳定后才清理；让自动化减少等待，不让自动化替用户承担不可逆风险。
