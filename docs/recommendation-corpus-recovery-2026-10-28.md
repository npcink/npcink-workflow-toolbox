历史请求正文和结果已不保留，故不补造逐批 skipped 数，也不声称排除了所有其他
历史影响因素。套餐限制是现有证据强支持的解释；先删除后检查仍是需修复的风险。

## 经验与下一步

1. 同时检查账号套餐和站点运行上限；站点 quota=ok 不能排除账号限额。
2. 运行结果未知时，先确认已提交键和旧 worker 状态；按实际差集续跑，
   不用重复投递制造“成功”，也不删除部分提交来凑齐批次。
3. 共享主机变更按已获授权执行；重启后核对运行版本与旧数据，禁止顺手部署。
4. 覆盖率采用完整来源集合与 Cloud 集合对比；编辑器抽样探针、语义质量、
   用户采纳分别记录，不能互相替代。

后续先由 Cloud 修复刷新先删除后校验输入/账号额度的风险，Addon 验证一次正常
增量投递及 Cron guard 的退出方案；Toolbox 单独修复状态双向 80/1000 截断。
随后在 npcink-eval-lab 基于已命名的完整语料与相同样本做 AI 主导相关性比较，
