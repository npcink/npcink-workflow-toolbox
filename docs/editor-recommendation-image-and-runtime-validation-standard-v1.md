# 编辑器推荐、图片与运行环境验证规范 v1

## 1. 目的与范围

本文记录单篇文章编辑器在站内引用推荐、向量召回、AI 特色图和
WordPress 写入路径上的共同开发原则。目标是让后续 AI 功能复用同一套
产品判断、反馈证据和验证分层，避免为每个按钮重复设计一套流程。

本文适用于 Toolbox 编辑器界面、Toolbox 本地 WordPress 写入，以及
Toolbox 对 Cloud 返回结果的消费。Cloud/Admin 的模型目录、能力验证、
Provider 路由和运行配置仍由 Cloud 负责；Toolbox 不建立第二套能力真相。

## 2. 一项界面只表达一个操作任务

### 2.1 站内引用建议

“内链候选”和“相关文章”不是两个独立的用户任务。用户真正要完成的是：
判断当前文章是否应该引用站内已有内容。因此统一为“站内引用建议”，再按
是否可直接采用区分结果：

- **可采用候选**：当前正文中存在精确、可定位且不位于代码块内的锚文本，
  可以生成明确的插入操作。
- **仅供参考**：主题相关，但没有安全的精确锚点；只展示标题、理由和打开
  文章入口，不伪装成可以自动插入的候选。

向量相似只能帮助发现候选，不能把“主题相近”自动升级为“适合插入”。最终
动作必须通过正文位置、重复链接、代码块和目标有效性等确定性规则。

### 2.2 信息与动作层级

候选项按以下顺序组织：

1. 先展示内容、命中依据和必要状态。
2. 在内容下方放一行主要动作，默认不超过三个。
3. 低频参数收进一个高级区域，但只有一个选项时直接展示，不使用折叠。
4. 没有持久业务结果的“忽略”不作为主要动作；若确实需要排除，必须说明
   排除范围、持续时间和恢复方式。
5. 批量选择只在用户明确进入批量模式后出现，不让日常单项采用承担额外
   认知负担。

界面状态应回答“现在发生了什么、下一步能做什么”，不重复解释已经由按钮、
字段或状态表达的内容。

## 3. 向量质量采用证据闭环

### 3.1 向量不是质量真相

向量召回负责缩小搜索范围，规则和排序负责形成候选，真实使用反馈负责判断
质量。没有经过人工校准前，不把任意相似度阈值翻译成“高度相关”等质量承诺；
可以展示来源、召回方式和原始状态，但必须保持含义诚实。

### 3.2 最小反馈数据

推荐质量至少需要以下可关联事件：

- 曝光：候选确实进入用户可见区域，是计算采用率的分母。
- 采用：用户执行了插入、引用或图片采用。
- 修改后采用：记录建议有价值但初稿不够准确。
- 拒绝或失败：区分用户判断、规则阻止和技术错误。
- 原生保存确认：对于编辑器内容，以文章真实保存后的状态作为最终结果证据。

事件应包含功能场景、候选标识、模型或检索版本、排序位置和可诊断的结果码，
但不上传不必要的正文、提示词或个人数据。

### 3.3 单人开发阶段的投入顺序

真实数据不足时不等待，也不伪造结论：

1. 先修确定性规则、候选去重、锚点定位和错误可解释性。
2. 用少量人工操作验证完整曝光到采用链路，可由开发者自己编写和审阅文章。
3. 用多个 AI 做离线复核、生成对抗样例或发现盲点，但不把 AI 互评当作真实
   用户标签。
4. 参考第三方开源项目的召回、重排和评测方法，不直接继承其阈值和质量结论。
5. 积累足够真实曝光与选择后，再训练权重、校准阈值或引入复杂重排。

是否进入第 5 步由数据覆盖和明确误差模式决定，而不是由固定“30 条 gold”
门槛决定。复杂方案只有在能解释并改善已观察问题时才值得引入。

## 4. AI 图片生成的操作者契约

### 4.1 字段含义

“画面描述”是用户可理解、可修改的中文创作意图，也是界面的主字段。英文
模型提示词是 Provider 传输细节：系统可根据中文描述生成或翻译，默认不展示，
只在诊断或高级检查中按需披露。人工修改中文描述后，应重新生成英文稿，避免
两份可编辑真相发生漂移。

图片生成结果应显示实际 Provider 和模型作为次级来源证据。界面不能只显示
运行配置名称，也不能在失败时让用户猜测最终调用了哪个模型。

### 4.2 运行状态与错误

- 没有画面描述时，不展示依赖它的生成控制和高级内容。
- 生成过程中禁用生成、方向参考和采用等冲突动作，保持尺寸稳定并明确进度。
- 不向用户透出原始 HTML 致命错误、内部异常栈或无法行动的 Provider 文案。
- 错误需归一为认证、能力不匹配、上游拒绝、超时、无候选、下载或 WordPress
  写入失败等可行动类别，同时保留结构化诊断码。
- 图片采用成功必须同步媒体附件、特色图和 Gutenberg 当前状态，不能只更新
  某一个界面预览。

## 5. 能力目录与运行验证的边界

第三方模型资料只能形成“该模型可能具备视觉、向量、图片或音频能力”的目录
假设。Cloud/Admin 在运行配置保存或显式验证时执行最小真实探测；成功后保存
验证证据，失败时拒绝把该实例用于对应能力。

Toolbox 只消费 Cloud 已路由的结果和来源信息，不复制模型白名单，也不自行判定
GPT、供应商或模型版本的能力。该规则同样适用于视觉、向量、图片生成、音频和
后续视频能力，避免模型增加时靠人工维护多套静态名单。

## 6. WordPress 运行环境验证分层

WP-CLI、PHP 测试进程和真实浏览器 REST 请求的 WordPress 引导环境并不等价。
一个路径通过不能替代其他层级：

| 层级 | 主要证明 | 不能单独证明 |
| --- | --- | --- |
| 静态/独立 PHP | 语法、契约、函数预加载依赖和纯逻辑 | 登录、nonce、编辑器同步 |
| WP-CLI / `rest_do_request()` | 路由、权限函数和服务端业务逻辑 | Web 引导环境、真实 HTTP 和浏览器状态 |
| 浏览器真实 HTTP smoke | 登录、nonce、REST 引导、按钮状态、附件写入和界面同步 | Provider 长期稳定性和生产部署 |

关键 WordPress 写入路径至少覆盖以上三层。浏览器 smoke 使用可清理的本地确定性
fixture，不为回归测试消耗 Provider 预算；同时验证临时文章、附件、登录辅助文件
和 MU fixture 均被清除。

本轮事故的直接教训是：WP-CLI 预先加载了 `wp_tempnam()`，使 CLI 测试通过，
但真实 REST 请求在插件命名空间内调用该函数时发生致命错误。Toolbox 的处理是
优先使用可用的 `wp_tempnam()`，否则用 `tempnam( get_temp_dir(), ... )` 创建临时
文件。没有直接加载 `wp-admin/includes/file.php`，因为该依赖扩大运行环境耦合，
并违反当前 WordPress.org 检查约束。

时间戳等跨系统值也应在契约边界做等价规范化。例如 UTC 的 `Z` 与 `+00:00`
是同一时刻；接受标准等价值比让每个调用方猜测字符串格式更简单，前提是只扩展
标准格式而不容忍模糊或无时区输入。

## 7. 收尾检查表

- 用户任务是否只有一个清晰名称，相关概念是否按结果类型呈现？
- 主动作是否紧邻内容且不超过必要数量？
- 单一选项、低频设置和“忽略”是否都有真实用途？
- 向量分数是否被误写成未经校准的质量结论？
- 是否具备曝光分母、采用结果和原生保存确认？
- 中文画面描述是否为唯一主编辑真相，英文稿是否保持传输细节？
- 运行中是否禁用冲突动作，错误是否可行动且不泄露原始内部信息？
- Toolbox 与 Cloud 的模型能力、路由和验证职责是否仍然唯一？
- 关键写入是否同时有独立 PHP、WordPress 业务和真实浏览器 HTTP 证据？
- 临时内容、附件、凭证辅助物和测试 fixture 是否可验证地清理？
