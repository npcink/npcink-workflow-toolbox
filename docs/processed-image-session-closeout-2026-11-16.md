## 开发经验与后续遵循

1. 从具体任务安排入口。ALT 依赖文章语境；图片格式属于压缩；选择图片是操作步骤，
   不为每个参数新增页面。删除重复入口时保留兼容合同和已保存数据。
2. 先证明一条完整路径，再谈扩展。预览、提交提案、审批、执行和媒体库落地分别取证；
   预览成功或得到提案 ID 都不是已保存，Toolbox 不能代替 Core 审批和 Toolkit 写入。
3. 保护审阅对象。处理选项变更使预览失效；仅切换保存目标不重跑 Cloud。写入时再校验
   原图指纹，避免把旧审阅应用于已经变化的附件。
4. 用可恢复性控制替换风险，用实际删除字节描述清理结果。保留旧文件仍占空间，
   依赖不明或校验失败应保留并说明原因，不能承诺“替换即省空间”。
5. 界面简化不能隐藏判断事实。审批状态、恢复期限、保留原因和失败重试就近显示；
   技术证据放文档／已有回执，不增加第二套后台管理真相。
6. 收尾时逐仓核查远端，不凭上次聊天中的“已清理”结论。Squash 后以 PR 最终 head
   与合并提交核对，删除前保全；混合修改、主工作区和其他会话资源分别记录。
7. 证据分层记录。本地、CI、合并、M4 接受、生产和人工接受互不替代；受控 fixture
   和自然使用也不混写。未知问题注明本轮未核实，保留入口，避免反复造数据。

这些经验解释现有合同，不新增产品能力、审批层或发布权限；产品边界和冻结规则继续有效。
